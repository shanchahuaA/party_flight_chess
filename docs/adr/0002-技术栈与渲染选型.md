# 技术栈与渲染：TS + Vite + Vue 3，棋盘 SVG + UI DOM

状态：accepted（2026-10-07）

## 决策

- 前端：**TypeScript + Vite + Vue 3**（`<script setup>`）。
- 渲染分两层：**棋盘层 SVG**（环形棋盘、终点支路、棋子），**UI 层 DOM**（手牌、抉择卡、世界消息流、玩家列表）。不上 Canvas，不上游戏引擎。
- **WS 消息协议类型只定义在 `shared/`**，client 与 server 共同导入，是协议唯一真源。

## 理由

- 本游戏 UI 的本质是「服务端快照 → 界面」的一条映射线（棋盘、手牌、世界消息全部由快照驱动）。Vue 的响应式正是干这个的；原生 TS 手写状态→DOM 更新，在联机状态同步下极易出现界面与状态漂移。
- 渲染技术的分界线是重绘频率。本局是事件驱动：几乎不重绘（走格动画、抽卡才有变化）。Canvas 的优势（高频重绘）用不上，成本（手写重绘循环、命中检测、帧管理）一点不少。SVG 声明式绘制一次，点击命中、viewBox 缩放适配手机屏、transform 逐格动画都是浏览器原生能力。
- 棋盘规模 ≤ 68 格、棋子 ≤ 8 个，SVG 性能上限绰绰有余；派对局首载一次，框架体积无压力。
- 游戏引擎（Godot/Phaser）已由地图决策排除（MVP 不上引擎）；本 ADR 只覆盖网页内的渲染与框架选型。
- 渲染选型与服务器负载无关：无论 SVG 还是 Canvas，服务器只发 WS 文本消息（见 ADR-0001 的协议原则），画图动作 100% 发生在玩家手机上。

## 后果

- 换框架 = 前端重写，故立此 ADR。
- 若未来「投屏大棋盘」等雾中事项带来高频重绘需求，重估条件是「单屏持续 60fps 重绘」，在此之前 Canvas 不再讨论。
